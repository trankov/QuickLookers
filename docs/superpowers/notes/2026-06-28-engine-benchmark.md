# Бенчмарк движка рендеринга — первый замер

**Дата:** 2026-06-28
**Контекст:** Task 6 плана движка (spike по бюджету производительности из дизайна).
**Машина:** Apple Silicon (arm64), macOS, Swift 6.3.

## Что мерили

Тёплый и холодный показ через `QuickLookersEngineFactory.makeDefault()`:
- Файл: 200 строк Swift (`let value = compute(x: 1, y: 2)`), ~6.4 КБ.
- **Холодный** показ: первый вызов — грузит грамматику `swift` и тему `dark-plus`, строит подсветчик.
- **Тёплый** показ: повторный вызов того же — грамматика/тема/подсветчик уже в памяти, только токенизация + сборка HTML.

## Цифры

| Конфигурация | cold | warm |
|---|---|---|
| debug (`swift test`) | 447 мс | 194 мс |
| release (`swift test -c release`) | 439 мс | 188 мс |

**Главный вывод по методике:** release почти не отличается от debug. Стоимость — **в JS-слое внутри JavaScriptCore** (Shiki + JS-движок регулярок `createJavaScriptRegexEngine`), а его оптимизация Swift-сборки не касается: JS исполняется интерпретатором JSC одинаково. Значит, debug-замер репрезентативен, и дальнейшие улучшения нужно искать не в флагах Swift-сборки.

## Оценка против бюджета

Ориентир дизайна — **~100 мс** на типичном файле. «Голый» движок на 200 строках даёт **warm ≈ 188 мс** — почти вдвое над бюджетом. Время растёт примерно линейно по объёму кода (токенизация построчная), поэтому:
- ~50–80 строк (первый экран) — ориентировочно **в пределах бюджета**;
- 200+ строк за один проход — над бюджетом.

## Рычаги (от дешёвого к дорогому)

1. **Кэш готового HTML** (подсистема расширения Preview). Повторный показ того же файла → Shiki не запускается вовсе, ~0 мс. Бьёт прямо в тёплый сценарий.
2. **Обрезка под первый экран.** Красим сразу первые ~50–80 строк (первая отрисовка в бюджете), остальное при прокрутке. Уже заложено в дизайн.
3. **WASM-Oniguruma вместо JS-движка регулярок.** Shiki с WASM-движком кратно быстрее на токенизации. Меняется за тем же протоколом `HighlightEngine`, объём — небольшой (нужен wasm-бинарь в ресурсах + загрузка в JSC), это НЕ полный нативный порт.
4. **Полный нативный порт** (Oniguruma C + Swift-токенизатор). Самый дорогой и рискованный путь (риск расхождения с VS Code на редких грамматиках).

## Решение

**Полный нативный порт пока не оправдан.** Сначала подключаем дешёвые рычаги (кэш + обрезка первого экрана) в подсистеме расширения Preview и при необходимости пробуем свап на WASM-движок. Повторно замеряем уже на реальном конвейере показа. Нативный порт — только если и после этого тёплый показ типичного файла не влезает в бюджет.

## Что зафиксировано в коде

`PerformanceTests.test_warmHighlightMeasured` оставлен как **измеритель**: печатает cold/warm, проверяет лишь, что тёплый кратно быстрее холодного (страховка от потери кэша подсветчиков) и не ушёл за абсурдный потолок. Жёсткого порога бюджета в юнит-тесте нет намеренно — бюджет проверяем на полном конвейере показа, а не на голом движке.

## Замер после Task 2 (218 языков + 54 темы)

**Дата:** 2026-06-28. После подключения полного набора Shiki (все 218 грамматик, 54 темы — ресурсы в бандле пакета).

| Конфигурация | cold | warm |
|---|---|---|
| debug (`swift test`) | 471.7 мс | 218.8 мс |

По сравнению с Task 1 (3 языка): холодный +25 мс, тёплый +25 мс. **Рост незначительный.** Причина — грамматики ленивые (загружаются по требованию при первом обращении к языку), а сам бандл Shiki не изменился; небольшой прирост объясняется фоновым шумом системы. Архитектурное решение (lazy-load грамматик по id) доказало себя: полный набор не влияет на тёплый путь.
