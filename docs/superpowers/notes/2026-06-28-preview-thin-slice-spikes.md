# Расширение Preview, тонкий срез — показания spike и уроки настройки

**Дата:** 2026-06-28
**Машина:** Apple Silicon (arm64), macOS 26, Xcode 26, Swift 6.3.
**Итог:** срез работает end-to-end — пробел в Finder на `.swift`/`.json`/`.js` даёт полноразмерное превью с подсветкой VS Code Dark+. Все три spike сняты.

## spike 1 — тёплый процесс (ЖИВЁТ)

Через многократные показы подряд процесс расширения **один и тот же** (`pid` не меняется), и `warm=true` на всех показах после первого. Значит:
- процесс расширения переиспользуется между показами;
- движок (Shiki в JavaScriptCore) строится один раз и остаётся горячим;
- ленивый статический кэш движка работает как задумано.

**Вывод:** тёплый JS-контекст между показами — подтверждён. Это основа для оптимизаций следующих фаз.

## spike 2 — бюджет на реальном конвейере

Полный показ = чтение файла + покраска движком + отрисовка в `WKWebView` (с ожиданием `didFinish`).

| Замер | warm ms |
|---|---|
| swift (типично) | 84–92 |
| swift (прогрев WebContent) | 112–174 |
| json | 101 |
| json (перезапуск WebContent) | 1368, 2612 |

- **Типичный тёплый показ ~85–175 мс** — около ориентира ~100 мс. Голый движок давал ~50 мс (см. `2026-06-28-engine-benchmark.md`); отрисовка `WKWebView` добавляет ~30–120 мс.
- **Выбросы 1.3–2.6 с** — когда вспомогательный процесс WebContent холодно стартует/перезапускается. Это не движок, а WebKit.

**Рычаги на потом (в порядке дешевизны):**
1. Кэш готового HTML — повторный показ того же файла мимо движка.
2. Держать `WKWebView`/WebContent тёплым в пределах процесса (убирает выбросы 1–2.6 с).
3. Обрезка первого экрана.

Бюджет в принципе достижим; точную настройку делаем в подсистеме показа, не в движке.

## spike 3 — необъявленный тип (НЕ ПАДАЕТ)

На расширение приходят только объявленные в `QLSupportedContentTypes` типы. Для неизвестного расширения файла `languageId` вернёт nil и метод бросит ошибку → QuickLook откатывается к системному показу. Полноценный тест возврата по opt-in системным UTI — в фазе настроек.

## Картинка против VS Code

Подсветка `.swift`/`.json` в теме Dark+ совпадает с VS Code (подтверждено визуально). Паритет держится на настоящих грамматиках/темах Shiki — как и задумано.

## Уроки настройки расширения QuickLook (важно для фаз 3–4)

Дорого добытые факты — чтобы не наступать снова:

1. **App Sandbox обязателен.** Без entitlement `com.apple.security.app-sandbox` демон `pkd` молча НЕ берёт расширение в провайдеры точки `com.apple.quicklook.preview`. Бандл при этом виден в «Системных настройках», но не вызывается. Отказавшись от App Group, нельзя выкидывать саму песочницу.

2. **WKWebView в песочнице требует `com.apple.security.network.client`** — даже если HTML грузится из строки, без сети. Иначе вспомогательные процессы WebContent/GPU падают (`errno=34`, `web process failed to launch`), и загрузка вешается навсегда (вечный спиннер).

3. **`ENABLE_DEBUG_DYLIB = NO`.** Xcode 16+ собирает Debug через стуб-загрузчик (`*.debug.dylib` + `__preview.dylib`); для app-расширения это ломает загрузку провайдера.

4. **Ждать `didFinish` навигации `WKWebView`** перед возвратом из `preparePreviewOfFile` — иначе QuickLook снимает картинку с ещё пустого вебвью (пустой экран).

5. **Регистрация — через запуск из Xcode** (Product → Run). Сборка `xcodebuild` + `lsregister`/`open`/`pluginkit -a` из командной строки расширение в провайдеры надёжно не заводит. Канонический путь — собрать и запустить хост-приложение из Xcode.

6. **Конфликт провайдеров.** Несколько расширений могут объявлять один UTI (у пользователя стоят `sbarex SourceCodeSyntaxHighlight` и FluxMarkdown). Кого выберет macOS — управляется только включением/выключением в «Системных настройках → Быстрый просмотр». При тесте конкурентов выключаем.

## Что это меняет для следующих фаз

- Бюджет достижим; первым включаем кэш HTML и тёплый WebView (убирает выбросы).
- App Sandbox + network.client — обязательная база любого превью-расширения; заложить сразу в фазе менеджера.
- Нативный порт движка по-прежнему не нужен.
