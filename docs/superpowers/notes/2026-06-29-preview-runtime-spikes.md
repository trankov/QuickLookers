# Рантайм-спайки показа в Finder — три находки (macOS 26, Darwin 25.5.0)

**Дата:** 2026-06-29. Проверено вживую пользователем на сборках фазы 5
(оптимизация показа). Эти вещи нельзя было поймать `swift test` — только живой
показ в Finder с системным логом. Все три добыты дорого, фиксируем, чтобы не
наступить снова.

Лог показа: `/usr/bin/log stream --info --predicate 'subsystem == "com.quicklookers.preview"'`
(поля `warm`, `cache`, `ms`).

## 1. Кэш HTML НЕЛЬЗЯ держать в групповом контейнере (App Group)

**Симптом:** `cache=false` на каждом показе, даже на повторном показе того же
файла. Папка кэша на диске не создавалась.

**Корень (лог ядра):**
```
Sandbox: QuickLookersPreview(pid) deny(1) file-write-create
  .../Group Containers/5FVC5YT2B5.com.quicklookers/Caches
```
Песочница **превью-расширения запрещает запись в групповой контейнер** — ни в
корень (`Caches`), ни в `Library/Caches`. Расширению групповой контейнер доступен
**только на чтение** (поэтому `settings.json` читается; пишет его приложение, не
расширение). Превью задумано «только смотреть».

**Фикс:** кэш HTML пишет и читает ТОЛЬКО расширение (приложению он не нужен;
общие — лишь настройки). Поэтому держим кэш в **собственном контейнере
расширения** через `FileManager.default.url(for: .cachesDirectory, ...)` →
`~/Library/Containers/com.quicklookers.QuickLookers.PreviewExtension/Data/Library/Caches/QuickLookersHTML`.
Туда расширение пишет свободно (там же WebKit сам создаёт свои папки). Инвалидация
по смене темы работает через ключ кэша (тема входит в ключ), кросс-процессная
синхронизация с приложением не нужна.

**Урок:** в превью-расширении App Group — это **канал чтения** (настройки,
библиотека), но не место для записи. Всё, что расширение пишет само, — в свой
контейнер.

## 2. WebContent усыпляется в простое → пустой экран ~1,4 с на первом показе после паузы

**Симптом:** время от времени показ «зависал» с пустым экраном; в логе — выбросы
`ms` 1100–2600 после пауз простоя 10–27 с. В активной серии показов выбросов нет
(6–100 мс).

**Корень (лог RunningBoard/jetsam):** вспомогательный процесс WebContent — **тот же
PID** на всём окне (не перезапуск, не падение), но его jetsam-приоритет качается
**40↔100**: 40 (фоновый, замораживаемый) в простое, 100 (активный) на показ.
Моменты подъёма до 100 точно совпадают с выбросами. Между показами QuickLook
убирает вебвью из окна → WebKit сигналит, что WebContent можно
деприоритизировать → в простое процесс замораживается → первый показ после паузы
платит за пробуждение.

**Фикс (публичный API, подтверждён доками WebKit и Apple):**
`WKPreferences.inactiveSchedulingPolicy = .none` (macOS 14+) — политика для
вебвью **вне окна**: `.none` держит его активным (не тормозит/не усыпляет), значит
WebContent не деприоритизируется. JS у нас выключен, поэтому «активность» почти
бесплатна. После правки выбросы исчезли даже при паузах 20–26 с (показ остаётся
3–10 мс).

## 3. Один общий вебвью ломает ПАРАЛЛЕЛЬНЫЕ превью (бесконечный спиннер)

**Симптом:** при одновременно открытых превью (панель Finder «Просмотр» +
QuickLook-пробел; режим галереи) в одной из панелей — **бесконечный спиннер** или
пустота. Последовательные показы при этом работали идеально.

**Корень:** «тёплый» общий статический `WKWebView` на весь процесс не может
обслужить два показа сразу. У него один конвейер навигации и один делегат:
- показ A грузит свой HTML, ждёт `didFinish`;
- показ B перехватывает тот же вебвью, переставляет делегата на себя, грузит свой
  HTML (навигация A прервана);
- `didFinish` приходит делегату B → разрешается континуация B; **континуация A не
  разрешается никогда → `preparePreviewOfFile` показа A висит → спиннер**.

**Фикс:** **пул тёплых вебвью** вместо одного общего. Каждый показ берёт свой
вебвью (`acquireWebView` — из пула или новый), на закрытии превью (`deinit`)
возвращает в пул (`releaseWebView`). Параллельные показы получают разные вебвью и
не сталкиваются; последовательные переиспользуют освободившиеся (тепло
сохраняется). Доступ к пулу — только с главного потока; возврат из `deinit`
страхуется хопом на главный поток (вебвью — UI-объект).

**Урок:** QuickLook показывает превью **параллельно**. Любое разделяемое на весь
процесс UI-состояние показа (вебвью, делегат, континуация) должно быть **на
показ**, а тёплый кэш таких объектов — через пул, а не синглтон.

## Итоговые замеры фазы 5 (тёплый процесс, кэш в своём контейнере)

- Холодный первый показ: ~300–430 мс.
- Тёплый промах кэша (движок + отрисовка): ~20–130 мс.
- Тёплое **попадание в кэш**: **~1,4–10 мс** (минует чтение и движок).
- Выбросов после простоя нет (`inactiveSchedulingPolicy=.none`).
- Параллельные показы оба отрабатывают (пул).
