# QuickLookers — дизайн-документ

**Дата:** 2026-06-27
**Статус:** утверждён, готов к написанию плана реализации
**Платформа:** macOS

## Контекст

Apple постепенно вытесняет старую архитектуру QuickLook-плагинов (`.qlgenerator`), и часть нужных пользователям плагинов для просмотра кода перестала работать. QuickLookers — это приложение под macOS, которое возвращает эту возможность современным, поддерживаемым способом: превью кода по нажатию пробела в Finder.

**Markdown — вне области продукта.** Для превью Markdown в Finder уже есть хорошее поддерживаемое решение (FluxMarkdown), дублировать его незачем. QuickLookers занимается только подсветкой кода; `.md`-файлы отдаём системе/стороннему плагину.

**Главная цель:** быстро, удобно и **визуально один-в-один как в VS Code**. «Привычно» здесь — не метафора, а требование: код должен краситься теми же грамматиками и темами, что использует VS Code/Cursor.

## Архитектура верхнего уровня

Две части, связанные общим контейнером:

- **Главное приложение** (GUI с настройками). Имеет доступ в сеть, может читать конфиг VS Code/Cursor. Управляет библиотекой тем и грамматик, импортом, настройками. Само умеет открывать и показывать любой файл (drag-drop / «Открыть с помощью…»).
- **Расширение QuickLook Preview** (полноразмерное превью по пробелу). В песочнице, в сеть не ходит, только рисует.
- **Общий контейнер (App Group)** — связующее звено: готовые темы, грамматики, кэш готового HTML, настройки. Песочница расширений видит только этот контейнер и сам просматриваемый файл.

Третья часть — **расширение QuickLook Thumbnail** (иконки в Finder) — **отложена**, см. раздел «Отложено до принятия решения о целесообразности».

Принцип разделения: **главное приложение — менеджер (читает/скачивает/импортирует/нормализует), расширения — потребители (берут готовое и рисуют).** Это и обходит ограничения песочницы: расширение не имеет права лезть в `~/Library/Application Support/Code/...`, поэтому всю подготовку делает приложение.

## Движок подсветки: Shiki

Подсветка в VS Code/Cursor основана на двух открытых вещах: **TextMate-грамматики** (`.tmLanguage`, определяют структуру кода) и **TextMate/VS Code-темы** (JSON, задают цвета). Shiki использует ровно их — поэтому даёт результат, совпадающий с VS Code, а не «похожий».

**Почему Shiki, а не альтернативы:**
- highlight.js / Highlightr — другой движок, цвета и разбор НЕ совпадают с VS Code. Отпадает по главному критерию.
- Tree-sitter — быстрый и нативный, но темы/токены другие, паритета с VS Code без большой ручной работы нет.
- Splash — только Swift, слишком узко.

**Возможности Shiki, которые используем (подтверждено документацией):**
- `loadTheme` — грузим тему VS Code напрямую из JSON.
- Загрузка любых грамматик из JSON.
- `codeToHtml` — готовый HTML (для показа в WebView).
- `codeToTokens` — токены с цветами (путь к нативному рендерингу, если понадобится).
- Полностью офлайн; есть JS-движок регулярок без WASM.

### Изоляция движка за интерфейсом

Логика «контент + язык + тема → HTML/токены» лежит за **единым интерфейсом** в общей библиотеке, которой пользуются и расширения, и приложение.

Стартуем на реализации **Shiki через `JavaScriptCore`**. Нативная реализация (линкуем C-библиотеку **Oniguruma** для точной семантики регулярок TextMate + переписываем на Swift только цикл токенизации из `vscode-textmate`; грамматики и темы остаются те же JSON) — **запасной путь, включаем только если бенчмарк покажет, что старт `JavaScriptCore` не влезает в бюджет.** Решение принимаем по замерам, не заранее (YAGNI). Причина осторожности: свой порт рискует расходиться с VS Code в редких грамматиках, а это бьёт по главной ценности продукта.

## Конвейер рендеринга

Принцип: **WebView не должен выполнять код — он получает готовый статичный HTML и только верстает его.**

1. **Покраска — в фоне, без браузера.** Shiki запускается в `JavaScriptCore` в процессе расширения (не внутри страницы), на выходе — готовый HTML с расставленными цветами.
2. **Показ — статичный HTML, JS выключен.** HTML отдаётся в `WKWebView` с отключённым JavaScript. Вебвью только верстает текст — самый быстрый и безопасный режим, снимает вопросы песочницы.

## Оптимизации

### В MVP

1. **Кэш готового HTML** в общем контейнере по ключу **(хэш содержимого файла + id темы + версия настроек)**. Файл не менялся и тема та же → отдаём из кэша, Shiki не запускается. Сброс по дате изменения файла и версии настроек.
2. **Тёплый JS-контекст** на время жизни процесса расширения: ядро Shiki и грамматики грузятся один раз, грамматики подгружаются лениво по расширению файла и остаются в памяти.
3. **Большие файлы — режем и догружаем.** Сразу рисуем первый экран (≈300–500 строк), остальное при прокрутке, для гигантских файлов жёсткий потолок с пометкой «показана часть». Это ещё и защита от убийства расширения системой по лимитам памяти/времени.
4. **Движок регулярок без WASM** (`createJavaScriptRegexEngine`) + **тонкие бандлы** Shiki: одна грамматика под расширение файла + одна активная тема.

### Заложить как хук, включать по замерам

6. Переиспользование одного `WKWebView` в пределах процесса вместо создания нового на каждый показ.
7. «Рендер-кит» из приложения: заранее подготовленная тема в формате Shiki + HTML/CSS-каркас + CSS шрифта в общем контейнере, чтобы расширение ничего не пересчитывало.
8. Предрасчёт светлой/тёмной версии для мгновенного переключения по системному виду.

**Бюджет производительности:** закладываем простой бенчмарк с целью порядка ~100 мс до появления картинки на типичных файлах, чтобы оптимизацию можно было проверять замером, а не на глаз.

## Форматы и языки

Два разных слоя — их важно не смешивать:

**Слой 1 — что умеем красить:** весь набор Shiki (~200 языков, ~60 тем), встроен в приложение (можно грузить лениво из бандла). «Установить язык» = включить уже встроенное.

**Слой 2 — что перехватываем в Finder по пробелу:** аккуратный набор, не все 200.
- **Код (opt-out):** включён по умолчанию, можно выключить. Стартовый набор: Python, JS/TS/JSX/TSX, C/C++, Java, Go, Rust, Swift, C#, PHP, Ruby, Kotlin, Dart, Scala, R, Perl, Vue, YAML, TOML, JSON, Dockerfile, SQL, GraphQL, Jinja.
- **Системные типы macOS (opt-in):** HTML, CSV, plist и прочее, что macOS показывает из коробки — **выключено по умолчанию**, отдаём системе, пока пользователь сам не включит.

**Языки не теряются, даже если не перехвачены в Finder.** Файл попадает к нам двумя путями: (а) пробел в Finder (нужен заявленный UTI); (б) открытие в самом приложении (UTI не нужен, откроет любой из ~200 языков).

Тема — **одна на всё, как в VS Code** (отдельная светлая и тёмная + «следовать за системой»). Тем под конкретный язык нет.

## Расширяемость (без сервера)

Своего маркетплейса и хостинга нет. Пополнение библиотеки из трёх источников, все ведут в общий контейнер:

1. **Встроенная коллекция Shiki** — ~200 языков и ~60 тем.
2. **Импорт из установленного VS Code/Cursor** — забрать тему/грамматику, которые у пользователя уже есть локально.
3. **Импорт `.vsix`/файла, скачанного пользователем самостоятельно** с маркетплейса VS Code. `.vsix` — это ZIP; главное приложение распаковывает, читает `package.json` (`contributes.grammars`, `contributes.themes`), достаёт файлы, нормализует и кладёт в контейнер.

Поскольку расширение скачивает **сам пользователь для себя** — вопрос редистрибуции/лицензий снят, мы ничего не раздаём.

Край: грамматика иногда ссылается на вложенные языки из другого расширения — если чего-то нет, показываем без подсветки этого вложенного куска, не падаем.

Маркетплейс с докачкой по сети — возможное будущее за тем же интерфейсом библиотеки, но не сейчас.

## UTI (перехват типов в Finder)

**Ограничение системы:** список перехватываемых типов задаётся статически в `Info.plist` расширения (`QLSupportedContentTypes`) на этапе сборки. Менять его на лету из настроек нельзя.

Отсюда модель:
- В плисте объявляем **широкий супернабор** типов (код по умолчанию + системные типы, которые хотим разрешить включать).
- Во время работы расширение может только **сужать**: для выключенного в настройках типа **вежливо отказывается** рисовать, показ возвращается системе.
- «Включить» тип, не объявленный в плисте, на лету нельзя.
- Поэтому opt-in системные типы тоже объявлены в плисте, но по умолчанию выключены и отдаются системе.

То же правило действует для Preview-расширения. Для отложенного Thumbnail-расширения — аналогично (свой плист), если оно появится.

**Spike перед реализацией:** проверить, что при отказе по объявленному системному типу показ действительно возвращается к родному превью macOS, а не ломается. Когда тип заявляют несколько провайдеров, выбор провайдера у macOS со своими правилами — это место легко «понадеяться и ошибиться».

## Настройки (состав окна)

- **Оформление:** выбор темы (отдельно светлая и тёмная + «следовать за системой»); импорт темы/шрифта из VS Code/Cursor; импорт `.vsix`/файла темы; шрифт и размер; нумерация строк; перенос строк; отступы.
- **Языки:** список всех языков с галочками «включён»; импорт грамматики (`.vsix` / `.tmLanguage.json`).
- **Перехват в Finder (UTI):** код (opt-out, можно выключить); системные типы (opt-in, выключено, включается с предупреждением о перекрытии родного превью macOS).
- **Превью и скорость:** лимит строк/размера для мгновенного показа; догрузка при прокрутке; кэш (размер, «очистить»). Переключатель иконок — только если Thumbnail-расширение будет реализовано (см. «Отложено…»).
- **Общее:** сброс к умолчаниям; «О программе».

## Цепочка выбора темы (приоритет)

1. Явный выбор пользователя в наших настройках.
2. Импорт из VS Code/Cursor (один раз, если установлены и пользователь нажал «импортировать»).
3. Встроенная тема по умолчанию (родные Dark+/Light+ из VS Code), по системному светлому/тёмному режиму.

Приложение **полностью самодостаточно**: без VS Code красит код его дефолтными темами и выглядит привычно. Зависимости от VS Code во время показа нет — тему мы копируем к себе; VS Code можно закрыть или удалить.

## Открытые технические проверки (spikes) перед/в начале реализации

1. **Возврат к родному превью macOS** при отказе расширения по объявленному системному UTI (см. раздел UTI).
2. **Бюджет производительности** конвейера Shiki/`JavaScriptCore` — измерить старт и решить, нужен ли нативный движок.
3. **Переиспользование процесса/контекста** расширением QuickLook — подтвердить, что тёплый JS-контекст реально живёт между показами.

## Проверка работоспособности (как тестировать end-to-end)

- Превью по пробелу в Finder для файлов разных языков; сравнить картинку с VS Code на тех же темах.
- Сценарий «без VS Code»: дефолтные темы, светлый/тёмный режим.
- Импорт темы из VS Code/Cursor и из `.vsix`; проверка, что после импорта VS Code не нужен.
- UTI: opt-out код перехватывается; opt-in системный тип по умолчанию отдаётся macOS, после включения — нам; после выключения — снова macOS.
- Скорость: повторный показ из кэша; большой файл (потолок и догрузка); бенчмарк против бюджета ~100 мс.

## Отложено до принятия решения о целесообразности

### Расширение QuickLook Thumbnail (иконки в Finder)

**Статус:** под вопросом — не уверены, что функция нужна и полезна. Реализацию **не начинаем**, пока не решим целесообразность.

Идея: отдельное расширение типа `QLThumbnailProvider`, которое рисует иконку файла кода в Finder (режим значков/галереи, без нажатия пробела).

Если решим делать:
- **Рендер нативный, без WebView.** На размере иконки текст нечитаем, поэтому Shiki/HTML/`WKWebView` не используем. Рисуем напрямую (Core Text / `NSAttributedString` → картинка): фон цвета темы + первые строки кода.
- **В песочнице,** отдельный таргет со своим `Info.plist` и `QLSupportedContentTypes`; правило сужения по UTI — как у Preview.
- Читает из App Group тему (для цвета фона) и список включённых типов.
- В настройках появляется переключатель «иконки вкл/выкл».
- Проверка end-to-end: иконки в Finder рисуются нативно и совпадают по фону темы.

Открытый вопрос даже внутри идеи: нужна ли вообще токенизация в иконке или хватит «фон темы + монохромный текст первых строк» — решать замером, если возьмёмся.
